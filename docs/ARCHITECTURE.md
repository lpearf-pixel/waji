# 系统架构

## 1. 边界

### 管理平台

Django 模块化单体，负责：

- accounts：用户、角色与权限
- devices：设备、机型、传感器和安装位置
- recordings：录音、采集批次、对象存储索引
- telemetry：转速、温度、压力、振动等结构化数据
- diagnoses：模型运行、异常分数、疑似故障和人工复核
- maintenance：检查、工单、换件和维修结果
- audit：关键操作与数据变更记录

初期保持单体部署，但模块间不共享私有服务层，便于后续按领域拆分。

### AI 服务

AI 服务独立部署，只通过稳定 API 或异步任务接收：

- 音频对象地址及校验值
- 设备和机型
- 工况、转速区间、负载和传感器位置
- 指定模型与阈值版本

返回异常分数、特征版本、疑似部位和可解释证据。AI 服务不得直接修改维修结论。

### 边缘代理

Rust 边缘代理负责采集、切片、校验、断网缓存、重试和 MQTT 状态上报。模型推理可作为后续插件加入，不与采集主进程强耦合。

## 2. 核心数据流

```text
传感器 -> 边缘代理 -> 对象存储/MQTT -> 管理平台
                                  -> AI 分析任务
AI 结果 -> 管理平台 -> 告警/工单 -> 技师确认 -> 训练数据闭环
```

## 3. 扩展原则

- 大文件进入对象存储，不进入 PostgreSQL。
- 高频遥测后续迁入 TimescaleDB 或专用时序库。
- 异步分析经 Celery 队列，按实时、批处理和训练拆分队列。
- 使用 Outbox 事件记录跨服务事件，避免业务事务与消息发送不一致。
- 所有模型和阈值均版本化，可回放历史数据。
