# Waji 两层系统工程 Skill 设计

日期：2026-07-18  
状态：已确认设计，已按起步阶段修订，等待书面规格复核  
目标仓库：`lpearf-pixel/waji`

## 1. 背景

Waji 是面向挖掘机、装载机和其他工程机械的声音、振动与维修知识辅助项目。项目最终可以发展到固定边缘监测，但起步阶段不假设每台机器具备持续在线采集条件。

当前最现实的业务起点是：机器出现异响、性能下降或疑似故障后，维修人员到现场，使用手机或低成本便携终端采集声音和必要的振动数据；老师傅依据听音、操作表现、故障码、压力测试和维修经验作出人工判断；系统保存采集过程、诊断假设、维修处理和维修后复测，逐步建立可追溯案例库。

固定边缘节点存在硬件、电源、安装、通信和售后成本。它应当是后续经过价值验证后的可选升级，而不是第一阶段的必备前提。项目应利用华强北在通用安卓设备、开发板、USB 音频、MEMS 传感器、小批量 PCB、线束和外壳方面的供应链优势，先形成一个成本可控、勉强可靠、维修人员能够携带使用的现场采集终端。

任何单一模块的局部成功都不能证明系统有真实维修价值：录到声音、生成频谱、模型准确率高或做出仪表盘，都不能替代“现场采集—人工判断—检查维修—复测验证”的闭环。

现有 `AGENTS.md` 已约束数据可追溯、模型版本、人工复核和模块接口，但尚未强制每次规划与开发围绕低成本起步、现场采集、专家经验沉淀、维修结果和阶段门展开。因此需要建立两层 Skill：

1. 通用工程机械健康与维修辅助系统工程 Skill；
2. Waji 项目专用适配层。

两层设计以“稳定使命与接口、低成本验证、证据分层、最小闭环、人工主导、可逆升级、阶段扩张”为核心。

## 2. 设计目标

### 2.1 通用层目标

通用层用于工程机械状态检查、现场故障采集、维修辅助、预测性维护、声音诊断、振动诊断、便携终端、边缘感知和多传感器工业 AI 项目。它应能够跨品牌、跨机器类型复用，不包含 CAT 型号、特定传感器、特定数据库或云平台实现。

通用层必须允许项目从人工采集和人工诊断起步，不能把持续边缘监测或 AI 自动诊断写成默认前提。

### 2.2 Waji 适配层目标

Waji 层将通用方法落实到当前项目，包括：

- CAT 挖掘机故障触发式现场采集；
- 手机或低成本便携终端采集机器声音；
- 必要时使用临时接触式声音或低成本振动传感器；
- 由维修人员主导故障判断和验证；
- 保存采集位置、操作工况、人工听音描述、检查步骤和维修结果；
- 建立维修前后可比较的声音与振动案例；
- 利用通用模块和小批量加工形成低成本终端；
- 只有在案例价值和经济性通过阶段门后，才评估固定边缘采集。

### 2.3 非目标

两层 Skill 不负责：

- 替代项目代码、测试或部署文档；
- 规定唯一的硬件品牌或软件框架；
- 要求第一阶段给每台机器安装固定采集盒；
- 宣称模型可以独立确定零件损坏；
- 绕过原厂安全规则、维修手册或技师判断；
- 在缺少维修结果时以离线准确率证明商业价值；
- 自动向原车控制网络发送报文；
- 自动执行停机、拆机或换件等高影响动作；
- 在案例量不足时提前训练复杂故障分类模型。

## 3. 方案选择

### 3.1 采用方案

采用“通用 Skill + 项目适配层”的两层结构：

```text
skills/
└── engineering-machinery-health-systems/
    ├── SKILL.md
    └── references/
        ├── system-blueprint-template.md
        ├── evidence-model.md
        └── stage-gate-template.md

projects/
└── waji/
    ├── PROJECT-SKILL.md
    └── references/
        ├── fault-triggered-field-capture.md
        ├── low-cost-portable-terminal.md
        ├── sensor-installation-contract.md
        ├── data-contract.md
        ├── diagnosis-review-contract.md
        └── validation-gates.md
```

### 3.2 选择理由

- 通用层保持技术与品牌无关，可复用于装载机、矿卡和其他工程机械；
- 通用层兼容人工检查、便携终端和固定边缘三种成熟度，不预设高自动化；
- 项目层可以快速迭代 CAT 现场采集和低成本终端细节，不污染通用方法；
- 触发规则明确：通用问题加载通用层，Waji 任务加载两层；
- 项目更换手机、麦克风、开发板、传感器、数据库或模型时，不需要重写系统工程原则；
- 新项目只需增加新的适配层。

### 3.3 被否决方案

未采用“所有资料放在一个 Skill 内”，因为项目资料会不断膨胀并降低通用性。未采用“两个完全独立 Skill”，因为会重复维护证据模型和阶段门，并造成触发冲突。

未采用“先部署固定边缘盒再收集数据”的默认路线，因为它会在业务价值尚未验证前引入高硬件成本、安装成本、车载供电风险、通信费用和现场售后负担。

## 4. 第一层：通用 Skill 规格

### 4.1 名称和触发条件

建议名称：

```yaml
name: engineering-machinery-health-systems
```

建议描述：

```yaml
description: Use when planning, reviewing, validating, rescuing, or scaling engineering-machinery field inspection, fault data collection, maintenance assistance, condition monitoring, predictive maintenance, acoustic diagnosis, vibration diagnosis, portable sensing, edge sensing, or multi-sensor industrial AI systems.
```

描述只说明触发场景，不概述内部流程，避免调用方只读描述而跳过正文。

### 4.2 核心原则

1. 将项目视为开放复杂系统，而不是功能清单。
2. 使命和接口保持稳定，实现必须可替换。
3. 自动化程度由证据和经济性决定，不以固定边缘采集为默认起点。
4. 优先采用最低成本、能完成真实闭环的工具和流程。
5. 原始观察、诊断假设、人工决定和维修结果分别存储。
6. 异常不等于故障，模型输出不等于事实，老师傅判断也必须通过检查或维修结果验证。
7. 先完成最小闭环，再扩展机器、故障类型、硬件复杂度和自动化程度。
8. 声音、振动、温度、压力、CAN、油液、故障码和专家意见保留独立证据。
9. 高影响或低置信度结论必须人工复核并支持回滚。
10. 系统验证包括采集成功率、判断可解释性、维修结果、人工工作量、成本和延迟结果。
11. 采集位置、设备差异、工况变化和传感器变化属于系统状态，不能当作随机噪声忽略。
12. 每次失败都应更新假设、采集协议、接口、模型或阶段门，并保留审计轨迹。

### 4.3 必需工作流

通用 Skill 被触发时，按以下顺序工作：

1. **使命与损失**：明确受益者、真实损失、不可接受伤害、时间范围和非目标。
2. **当前成熟度**：明确项目处于人工采集、便携终端、半自动采集还是固定边缘监测阶段。
3. **系统边界**：区分控制、观察、推断和未知项，列出人员、环境、机器、外部平台和约束。
4. **最低成本闭环**：优先寻找无需固定安装即可完成的观察—判断—检查—维修—复测闭环。
5. **总设计**：拆分现场采集、数据管理、信号处理、案例检索、专家复核、维修和评估子系统。
6. **证据分层**：观察、假设、决定、结果分离，保存支持证据、反证、置信度和替代解释。
7. **综合集成**：根据优势组合标准流程、专家经验、规则、统计方法、AI、仿真和人工复核。
8. **可逆更新**：版本化采集协议、设备、传感器、模型、阈值、配置和人工操作。
9. **系统验证**：评估现场重复性、维修结果、人员接受度、成本、安全和工作量。
10. **阶段门**：只在证据阈值通过后增加硬件、设备、部件、用户或自动化。
11. **反馈更新**：复盘采集失败、误判、维修无效、设备不兼容和人员拒用。

### 4.4 输出契约

通用 Skill 的正式输出必须依次包含：

1. 使命和非目标；
2. 当前项目成熟度和成本约束；
3. 利益相关方和系统边界；
4. 场景、数据流和反馈环；
5. 最低成本最小闭环；
6. 子系统及接口契约；
7. 观察—假设—决定—结果模型；
8. 指标和验证；
9. 人工复核和升级；
10. 风险、未知项和可逆决定；
11. 阶段门及进入条件。

未明确最低成本闭环、事实与推断分离、高影响决策复核或硬件升级依据时，输出必须返回设计阶段，不能用增加功能或采购昂贵硬件替代缺失条件。

## 5. 第二层：Waji 项目适配规格

### 5.1 触发条件

以下任务必须加载 Waji 项目层，同时加载通用层：

- 修改 `waji` 仓库架构、现场采集、便携终端、边缘端、数据平台或 AI 诊断；
- 设计 CAT 或其他挖掘机故障现场录音；
- 讨论手机录音、麦克风、接触式传感器、采样位置、工况和数据契约；
- 设计老师傅听音记录、技师复核、维修工单和维修后复测；
- 设计华强北通用模块组成的低成本终端；
- 计划从人工采集升级到固定边缘采集；
- 使用模型准确率、仪表盘或单次案例证明项目成功。

### 5.2 项目使命

在不干预原车控制、不过早增加固定硬件成本的前提下，当机器出现故障征兆或异响时，帮助现场人员按统一流程采集声音和必要的振动证据，记录老师傅的判断依据，并通过检查、维修和维修后复测形成可复用案例。系统逐步把个人经验转化为可检索、可比较、可验证的维修知识。

### 5.3 项目非目标

第一阶段明确不做：

- 给所有机器安装固定边缘节点；
- 连续 7×24 小时监测；
- 自动报警或自动停机；
- 向原车 CAN 发送报文；
- 仅凭声音确定具体零件；
- 跨所有 CAT 型号使用一个基线；
- 在没有真实维修结果时发布故障准确率；
- 精确剩余寿命预测；
- 替代 CAT 原厂故障码、油液分析、压力测试和维修手册；
- 在人工案例不足时把复杂 AI 模型作为主产品。

### 5.4 Waji 起步阶段最小闭环

```text
机器出现异响、性能下降或疑似故障
→ 维修人员携带手机或便携终端到现场
→ 按指定位置、距离和动作采集声音
→ 必要时临时安装接触式声音或低成本振动传感器
→ 记录机型、工时、温度、动作、负载和现场环境
→ 老师傅听音并记录一个或多个诊断假设
→ 结合故障码、压力、油液和拆检进行人工判断
→ 维修、调整、排除或继续观察
→ 在相同位置和相近工况进行维修后复测
→ 保存维修前后数据、人工依据和最终结果
→ 将案例加入可检索案例库并修订采集规则
```

只有完成“现场采集—人工假设—检查或维修结果—复测”，才算完成一次闭环。只有一段录音、只有老师傅口头判断、只有频谱或只有维修结果，都不构成完整案例。

### 5.5 三阶段产品路线

#### 阶段 A：人工现场采集

以现有安卓手机或 iPhone 为主要采集设备，配合统一采集 App、外接麦克风和纸面或电子采集卡。目标是验证采集流程、案例字段和维修闭环，不追求专用硬件。

#### 阶段 B：低成本便携终端

利用华强北通用供应链形成维修人员随身携带的终端。它不是固定装车设备，采用电池供电，工作时临时靠近机器或连接临时传感器，完成：

- 引导式采集；
- 声音质量检查；
- 设备、位置和工况选择；
- 本地保存与断网导出；
- 频谱和历史案例初步对比；
- 老师傅语音或文字结论记录；
- 维修后复测关联。

终端优先使用成熟通用模块：低成本安卓主板或 ARM 开发板、触摸屏、USB 音频接口、空气麦克风、可选接触式拾音器或 MEMS 加速度模块、移动电源或锂电池组、小批量外壳和线束。设计目标是“现场勉强可靠且易维修”，而不是第一版达到工业车载等级。

第一版终端的设计 BOM 目标控制在人民币 1,000–2,500 元区间；该数字是项目成本目标，不是供应商报价承诺。超过目标时必须说明增加成本换取的具体证据价值。

#### 阶段 C：固定边缘监测

只有当现场案例证明某些高价值故障存在明显提前征兆、人工巡检来不及捕获且固定监测的年度收益高于硬件与运维成本时，才选择少量机器安装固定节点。固定边缘采集是后续独立子项目，不能反向绑架阶段 A 和阶段 B。

## 6. Waji 子系统与接口

| 子系统 | 负责 | 明确不负责 | 关键接口 |
|---|---|---|---|
| 故障事件登记 | 记录报修原因、现象、机器和现场联系人 | 判断故障部位 | 事件编号、设备信息、问题描述 |
| 现场采集流程 | 引导位置、距离、动作、时长和重复次数 | 自动确认故障 | 采集任务、质量结果、原始文件 |
| 手机/便携终端 | 录音、临时振动采集、离线保存、案例关联 | 取代工业固定监测 | 采集包、设备状态、导出接口 |
| 传感器与临时安装 | 采集物理信号、记录位置方向和连接方式 | 输出故障结论 | 安装记录、校准记录、样本流 |
| 数据平台 | 设备、事件、采集包、人工判断、维修结果、权限和审计 | 覆盖原始数据 | REST/API、对象索引、审计事件 |
| 特征服务 | 频谱、能量、脉冲、相似度等可重复计算 | 下达维修命令 | 特征版本、输入校验值、结果证据 |
| 案例检索 | 查找同型号、同部位、相似声音和历史维修案例 | 把相似案例当作当前事实 | 相似案例、差异和出处 |
| 诊断辅助 | 汇总老师傅意见、规则、特征和替代解释 | 隐藏来源分歧 | 诊断假设、证据引用、建议验证 |
| 技师工作台 | 复核、检查、维修、排除、复测 | 修改历史原始记录 | 决定、结果、换件、照片、备注 |
| 固定边缘系统 | 后期持续采集、缓存和上传 | 作为起步阶段前提 | 批次清单、状态和对象地址 |
| 评估系统 | 采集成功率、案例闭环率、诊断帮助度、成本和工作量 | 只报告模型准确率 | 试点报告、阶段门结论 |

## 7. 证据数据模型

### 7.1 Observation：观察事实

必须可追溯到现场录音、视频、临时传感器、仪表、人工检查或外部系统。例如：

- 主泵附近在举升动作时出现周期性尖锐声；
- 手机距发动机舱左侧 50 厘米录音 20 秒；
- 同一动作重复三次均出现相同声音；
- 发动机转速约 1750 RPM；
- 液压油温为 82℃；
- CAT 故障码列表中无当前活动报码；
- 技师观察到吸油管路存在气泡；
- 维修后相同位置录音中异常声消失。

### 7.2 Hypothesis：诊断假设

假设示例：主泵气蚀、轴承冲击、管路共振、护板松动、排气泄漏、环境干扰或录音位置不一致。每个假设必须包含：

- 提出者；
- 支持证据；
- 反对证据；
- 替代解释；
- 置信度；
- 建议验证动作；
- 规则、案例或模型版本。

老师傅结论在检查确认前属于 `Hypothesis`，不能直接写成 `Outcome`。

### 7.3 Decision：人工决定

例如继续观察、重新录音、复装护板、压力测试、检查吸油管路、停机拆检或更换滤芯。必须记录决定人、时间、依据、风险和可撤销方式。

### 7.4 Outcome：验证结果

例如确认滤芯堵塞、确认护板松动、未发现机械损坏、更换部件后异响消失、维修后声音未变化或异常来自录音干扰。结果必须尽量关联维修前后相同位置和相近工况的数据。

系统禁止用 `Hypothesis` 覆盖或冒充 `Outcome`。

## 8. 低成本便携终端约束

### 8.1 必需能力

第一版终端必须具备：

- 单手或双手可携带；
- 电池供电，不接入原车电气系统；
- 至少一个可靠的外接音频输入；
- 保存原始无损或低损音频；
- 显示录音电平、削波和背景噪声；
- 选择设备、部位、动作和采集位置；
- 每个动作支持重复录制；
- 无网络时完整工作；
- 通过 Wi-Fi、USB 或存储卡导出；
- 支持现场备注、语音说明和维修后复测关联；
- 模块损坏后能够低成本替换。

### 8.2 可选能力

- 接触式压电拾音器；
- 低成本三轴 MEMS 加速度模块；
- 红外测温或外接温度探头；
- 蓝牙或 USB 转速输入；
- 本地频谱和历史案例相似度；
- 摄像头拍摄安装位置和仪表状态。

### 8.3 起步阶段禁止项

- 为追求外观先定制昂贵模具；
- 在没有案例价值时采购工业级高价采集卡；
- 将便携终端直接接入原车 CAN 并发送报文；
- 为了压低成本取消原始数据保存；
- 使用无法记录设备、位置和工况的普通录音文件作为正式案例；
- 把本地相似度或模型结果显示为确定故障。

## 9. Waji 安全与人工复核

- 第一阶段采用人工现场采集，不接管控制；
- 便携终端优先电池供电，不从机器电源取电；
- 数据采集人员不得在无资质情况下操作机器；
- 需要机器动作时，由合格驾驶员按采集指令执行；
- 采集人员不得进入回转半径、工作装置下方或高温运动部件附近；
- 临时传感器必须在停机、卸压和安全确认后安装；
- CAN 接入属于后续能力，必须隔离、只读并默认无发送能力；
- AI 只输出相似案例、异常证据、疑似部位、置信度、反证和建议检查；
- 自动停机、拆机、换件属于高影响动作，必须经过技师和安全负责人；
- 低置信度、证据冲突、未知工况和采集质量差必须升级人工复核；
- 人工结论与模型结论发生分歧时，保留双方记录并安排验证，禁止静默覆盖；
- 原始数据、模型结果、人工修改和维修结果都必须不可变审计。

## 10. 指标与验证

### 10.1 现场采集质量

- 从接到报修到完成采集所需时间；
- 采集任务完成率；
- 录音削波、噪声过大和位置错误比例；
- 同一动作重复录音的一致性；
- 设备、部位、动作、距离和环境字段完整率；
- 原始文件校验和可回放性；
- 维修前后可比较样本比例。

### 10.2 人工诊断与案例质量

- 老师傅是否能够说明判断依据；
- 不同技师对同一案例的意见一致性；
- 假设是否包含支持证据和反证；
- 从采集到明确维修或排除结果的闭环率；
- 相似案例是否减少查找和判断时间；
- 最终结果与初始判断的差异；
- 错误换件、不必要拆检和漏检情况。

### 10.3 便携终端

- 单台 BOM 是否达到项目目标；
- 开机、采集、保存和导出成功率；
- 电池续航；
- 无网络可用性；
- 模块替换与维修成本；
- 技师培训时间；
- 与手机直接采集相比，数据完整度和可重复性是否提升。

### 10.4 模型与算法

起步阶段算法只作为辅助指标：

- 同一案例维修前后声音差异是否可检测；
- 相似案例检索是否返回合理结果；
- 按设备和工况划分后的泛化表现；
- 算法结论的校准和不确定性；
- 对环境干扰、位置变化和设备差异的鲁棒性；
- 算法是否实际减少技师工作量。

### 10.5 维修与商业价值

- 采集和案例系统是否帮助定位检查方向；
- 是否减少重复到场和无效拆检；
- 是否减少错误换件；
- 是否缩短故障确认时间；
- 是否形成可用于培训新维修人员的案例；
- 单次案例价值与采集、终端、平台和人工成本比较；
- 固定边缘监测的潜在收益是否足以覆盖完整生命周期成本。

## 11. 阶段门

### Gate 0：人工采集协议可执行

进入条件：形成明确的报修登记、声音采集位置、距离、动作、时长、重复次数、现场安全和维修后复测协议；使用普通手机完成至少一次完整演练；所有原始数据可回放并关联设备和事件。

### Gate 1：人工故障案例闭环

进入条件：至少形成 5 个完整案例，其中至少 3 个具有明确维修、排除或调整结果；维修前后数据可比较；关键字段完整率不少于 90%；老师傅判断依据已经结构化保存。

Gate 1 未通过前，不把固定边缘硬件和复杂 AI 模型作为主要开发方向。

### Gate 2：低成本终端原型

进入条件：终端完成引导录音、质量检查、离线保存、数据导出和人工结论记录；设计 BOM 位于人民币 1,000–2,500 元目标区间，或对超出部分给出明确价值依据；终端不接入原车控制与供电系统。

### Gate 3：便携终端现场试点

进入条件：至少由 2 名现场人员在 10 次故障或检查任务中使用；有效采集率不少于 90%；无网络情况下可用；与普通手机自由录音相比，终端明显提升元数据完整度、重复性或案例可用性；未产生不可接受的现场安全问题。

### Gate 4：案例辅助诊断有效

进入条件：案例检索、频谱或规则至少在 5 次独立任务中对技师检查方向产生可记录帮助；系统保留反例和误导案例；不存在把相似声音直接当作确定故障的流程；技师工作量可接受。

### Gate 5：固定边缘需求成立

进入条件：已经识别出一个或多个高价值故障，其征兆在故障发生前可持续出现，人工到场采集无法及时捕捉；估算的年度避免损失高于固定硬件、安装、通信、维护和人工复核成本；明确选择需要持续监测的部位和工况。

未通过 Gate 5，不为全部机器采购固定边缘节点。

### Gate 6：固定边缘小规模试点

进入条件：只选择少量代表性机器；供电、安装、通信和数据质量稳定；固定采集结果能够与已有现场案例和维修结果关联；误报工作量可接受；通过试点后再讨论扩大部署。

### Gate 7：商业扩张

进入条件：人工采集或边缘监测对客户产生可量化维修价值；终端和平台使用流程可复制；年度收益高于完整成本；误判未造成不可接受的无效拆机；客户维修团队愿意持续使用并贡献维修结果。

## 12. Skill 测试设计

创建 Skill 时采用文档 TDD。先在不加载新 Skill 的情况下运行压力场景，记录基线失败和合理化语言；再编写 Skill，重复测试并关闭漏洞。

### 12.1 必测压力场景

1. **要求立即给全部机器安装边缘盒**：应要求先完成手机现场采集和维修闭环，除非已有充分经济证据。
2. **硬件越贵数据越专业**：应比较新增成本是否带来不可替代的证据价值，优先低成本可维修模块。
3. **老师傅听完说主泵坏了**：应把结论记录为假设，并要求压力、拆检、维修或复测验证。
4. **故障发生时只有一段手机录音**：应保存但标记证据限制，并争取同位置复录、维修后样本和环境信息。
5. **录音位置变化导致频谱变化**：应优先检查采集协议和位置一致性，而不是判断机器恶化。
6. **客户要求终端直接自动判断并停机**：应识别为高影响控制，禁止便携辅助终端直接执行。
7. **只有少量案例但要求训练深度模型**：应优先案例库、规则和相似度工具，并明确数据不足。
8. **为了赶进度跳过维修结果**：应阻止以录音数量、频谱图或模型训练替代闭环。
9. **华强北模块可靠性一般**：应通过模块化替换、采集质量检查和备件策略管理，而不是假装达到工业等级。
10. **已有便携终端后默认升级固定边缘**：应要求通过 Gate 5 的持续监测需求和经济性证据。

### 12.2 通过标准

- 正确识别 Skill 触发场景；
- 按输出契约生成系统工程蓝图；
- 能根据当前成熟度选择手机、便携终端或固定边缘路线；
- 不把老师傅判断、算法异常或相似案例写成事实；
- 明确最低成本最小闭环与当前阶段门；
- 高影响决策有人审与回滚；
- 在时间、成本和扩张压力下仍不跳过验证；
- 不因追求专业外观和硬件参数提前增加无证据成本。

## 15. 验收结论

本设计通过后，下一步不是直接编写所有文件，而是先为 Skill 编写详细实施计划，包含基线压力测试、最小 Skill 内容、参考模板、项目适配、仓库集成和验证顺序。

Skill 只有在基线失败已记录、加载后压力测试通过并完成自检后，才可标记为可用。Waji 的第一阶段交付目标是现场采集协议和人工维修案例闭环；低成本便携终端是第二阶段；固定边缘采集必须通过独立的需求与经济性阶段门。
