# Gate 0 现场采集演练手册

## 1. 演练目的

Gate 0只验证以下最小闭环是否能够由现场人员执行：

```text
手机系统录音机录音
→ 手机网页上传原始录音和位置照片
→ Observation
→ 老师傅 Hypothesis
→ 人工 Decision
→ 检查/维修 Outcome
→ 同位置维修后复测
→ verified_complete
```

本次演练不验证故障诊断准确率，也不允许据此采购固定边缘设备。

## 2. 人员

至少安排：

- 一名合格设备操作手；
- 一名现场采集人员；
- 一名维修技师或老师傅；
- 一名复核人员，可以与维修技师为同一人，但必须明确记录身份。

采集人员没有操作资质时，不得操作设备。所有动作由合格操作手控制。

## 3. 安全停止条件

出现以下任一情况，立即停止采集：

- 人员需要进入回转、行走、属具或落物危险区域；
- 需要接近风扇、皮带、高温表面、高压油路或运动部件；
- 无法维持约定的安全距离和固定录音位置；
- 操作手、维修负责人或现场安全负责人要求停止；
- 天气、粉尘、噪声或其他设备使本次协议无法可靠执行。

系统不会自动授权开机、动作或停机。

## 4. 演练前准备

### 系统

```bash
docker compose up --build
docker compose exec platform python manage.py createsuperuser
```

管理员登录 `/admin/` 创建现场账号，或直接使用管理员账号完成首次演练。

### 手机

- 确认系统录音机可以导出录音文件；
- 开启免打扰模式；
- 保留足够存储空间；
- 不用手指遮挡麦克风；
- 准备拍摄录音位置照片；
- 不要在录音完成前删除手机本地原件。

### 设备与事件

事先确定：

- 设备场内编号；
- 品牌、型号、序列号和工时；
- 当前症状；
- 安全可重复的动作；
- 录音部位和固定参照物；
- 维修前、维修后都可以重复的位置和方向。

## 5. 录音协议

### 5.1 环境声

目标设备安全停机时，先录制约10秒环境声。记录：

- 是否有风声；
- 是否有其他设备；
- 是否有人讲话；
- 是否有破碎机、运输车或其他持续噪声。

环境声不可安全取得时，在事件环境说明中写明原因。

### 5.2 维修前录音

对同一个安全动作，尽量完成三次录音：

1. 手机位置不变；
2. 麦克风方向不变；
3. 机罩/门状态不变；
4. 设备动作、负载和转速尽量一致；
5. 每次录音结束后单独保存，不合并覆盖。

每次录音都拍摄或复用清晰的位置照片，并填写：

- 部位/区域；
- 固定位置文字；
- 距离；
- 麦克风方向；
- 机罩状态；
- 动作；
- 负载；
- 显示转速；
- 重复序号；
- 现场杂音。

## 6. 网页录入顺序

### 6.1 登录

打开：

```text
http://<服务器地址>:8000/field/
```

### 6.2 登记设备

点击“登记设备”，填写场内编号、品牌、型号、序列号和工时。

### 6.3 创建故障事件

点击“新建故障事件”，描述可观察症状，例如：

```text
怠速抬大臂时主泵区域出现间歇性尖锐声，动作暂未发现明显变慢。
```

不要在触发事件里直接写“主泵已损坏”。

### 6.4 上传环境声和维修前录音

依次选择：

- `环境声`；
- `维修前`。

上传后确认页面分别显示：

- 原始录音；
- 原始SHA-256；
- 质量状态；
- 轻度去噪试听副本，或透明的处理失败状态。

原始录音上传成功后不得替换。录错时新建另一条采集记录，并标记原记录质量问题。

### 6.5 记录 Observation

Observation只写可观察事实，例如：

```text
抬大臂动作开始后约1秒出现尖锐声，停止动作后声音消失。
```

不要写：

```text
主泵气蚀。
```

后一句属于Hypothesis。

### 6.6 记录 Hypothesis

至少填写：

- 疑似部位；
- 疑似失效模式；
- 支持证据；
- 反对证据；
- 替代解释；
- 置信程度；
- 缺失证据；
- 最安全的下一步验证。

示例：

```text
Hypothesis：吸油滤芯堵塞或吸油管路进气。
支持：声音只在液压动作时增强。
反对：尚无压力、油液和拆检证据。
替代解释：主泵磨损、油温异常或录音位置干扰。
下一步：合格维修人员停机检查滤芯和吸油管路，并按维修手册测压。
```

### 6.7 记录 Decision

Decision必须写明谁授权、风险和可逆性，例如：

```text
由维修负责人授权，在计划停机窗口检查吸油滤芯和管路；检查前不执行高负载连续作业。
```

系统的声音处理结果不能自动下达停机命令。

### 6.8 记录 Outcome 或未解决状态

Outcome必须由检查、测量、维修、排除或复测证据建立。

示例：

```text
拆检发现吸油滤芯污染，更换并排气后，同位置同动作录音中的尖锐声显著降低。
```

现场暂时无法停机检查时，记录明确未解决状态，并填写：

- 无法闭环原因；
- 下次复核条件；
- 负责人；
- 截止日期。

## 7. 维修后复测

维修或调整完成后：

1. 使用与维修前相同的固定位置；
2. 保持距离、方向、机罩状态、动作、负载和转速尽量一致；
3. 选择采集阶段“维修后”；
4. 关联对应维修前录音；
5. 上传位置照片和原始录音；
6. 在Outcome中选择维修后录音；
7. 填写维修前后对比和剩余不确定性。

## 8. 完整度验收

### incomplete

任一核心证据缺失：

- 有效维修前录音及上下文；
- Hypothesis；
- Decision；
- Outcome或明确未解决状态。

### complete

核心闭环已经建立，但没有可比较的维修后录音。

### verified_complete

核心闭环完整，并且存在有效或有杂音但可用的维修后录音。

Gate 0演练目标是页面显示：

```text
验证完整
```

## 9. 原始与去噪试听检查

老师傅和复核人员分别试听：

- 原始录音；
- 轻度去噪试听副本。

记录以下结论：

- 关键冲击、啸叫、摩擦或周期变化是否仍能听到；
- 去噪是否产生新的假音；
- 去噪是否改变诊断方向；
- 原始录音是否因削波、静音、手持摩擦或竞争设备而需要重录。

任何情况下都以原始录音为证据源。

## 10. 演练证据留存

保留以下截图或记录：

- 登录后的现场台账；
- 设备和故障事件；
- 维修前录音及SHA-256；
- 原始/去噪双播放器；
- Observation；
- Hypothesis及反对证据；
- Decision及授权人；
- Outcome或未解决状态；
- 维修后录音关联；
- `verified_complete` 状态。

不要把真实客户隐私、人员身份证明、私人电话或未授权的商业资料放入公开截图。

## 11. Gate 0 通过记录

演练完成后记录：

```text
演练日期：
设备编号：
事件编号：
采集人员：
操作手：
维修/复核人员：
原始录音数量：
维修后录音数量：
最终完整度：
发现的协议问题：
需要修改的字段：
是否建议进入下一次演练：
```

一次演练通过只证明协议可以执行，不等于Gate 1通过。Gate 1仍要求至少5个完整案例、3个明确Outcome和至少90%的关键字段完整率。
